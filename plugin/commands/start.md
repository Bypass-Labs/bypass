description: Connect an application and approve a security test in a few choices.
---

Start with `bypass_onboarding`; this command contains the setup instructions, so load the full bypass skill only when beginning assessment. Pass repository, URL, environment and review type already supplied in the conversation. Use the next action embedded in each tool result instead of rereading onboarding after every step.

1. If the review type is unknown, open its native picker: Code only, Code + running app, Running app only. Retain custom instructions. Suggest the current folder only if the tool confirms it contains application source. A home directory is not an application. Connect a supplied Git URL before proceeding with code setup; app-only needs no repository.
2. Ask only for a missing URL/path. Use the native environment picker only if the environment is unknown. Retain supplied answers. Continue automatic setup actions without asking whether to continue.
3. Show the compact proposed test scope: app, environment, paths, methods and rate. Ask **Do you control this app and authorize these tests?** with **Approve**, **Decline**, **Custom instructions**. Use the returned picker. Approve explicitly confirms control and the displayed scope; a preselection or custom note is not approval. Explain write-method effects briefly. Show advanced method/path choices only when requested. If custom instructions change the plan, show the updated plan before approval. Decline saves setup and runs nothing.
4. Domain verification is configured with project setting `ownershipVerification`: off, dns, or http. New projects use off; existing projects keep their setting. Show DNS TXT or HTTPS-file steps only when required. Never call an operator acknowledgment verified ownership. On request, use `bypass_config` and `bypass_set_config`; do not ask the user to edit JSON. Changing this setting clears testing permission.
5. After approval, authorize the exact displayed scope, including production only if shown and approved, then continue the requested review. If the user asked only for setup, finish with setup saved. Load the bypass skill before assessment. Accounts are optional; reuse saved accounts and discover missing configuration. Account creation needs its own explicit permission unless already granted. Do not edit application code to fix findings without a separate request.

For Running app only, follow the wizard’s bypass_blackbox_setup action with its approved URL, paths, methods, rate and environment. Ask only for missing Muse-call and minute limits (defaults 120 and 30), then start the blackbox audit and drive next/submit through verification and export. For Code only or Code + running app, use bypass_scan.

Keep each setup response to the current stage and one needed input. Do not repeat Done / Now / Next, print the internal checklist, expose MCP syntax or restate installer permission notices. Show a brief progress update during meaningful waits, with actual elapsed time and no invented ETA. During assessment, continue the agreed work after each finding and report actual completed/blocked counts.
