For a bare `/bypass:blackbox`, ask **only**: "What target URL should I audit?" Then wait for the answer. Do not show a list of missing settings or call a setup tool yet.

Collect the remaining settings in this order, **one question per reply**, waiting after each answer:

1. **Allowed paths:** "Which paths may I audit? Say `all paths` for `/`, or give prefixes such as `paths: /api,/rest`."
2. **Allowed methods:** "Which HTTP methods may I use? Default: `GET,HEAD,POST,PATCH,DELETE`. Enter `default` or a comma-separated list."
3. **Request rate (RPS):** "What request rate should I use? Enter a positive number, such as `5` RPS."
4. **Muse calls (default 120):** "How many Muse calls may this audit use? Enter a positive whole number or `default` for 120."
5. **Time limit in minutes (default 30):** "How many minutes may this audit run? Enter a positive number or `default` for 30."

If the invocation or an earlier answer already supplied a setting, skip its question. If one answer supplies several settings, retain all of them and ask only the next missing one. Interpret `all paths` as `/` and `default` methods as `GET,HEAD,POST,PATCH,DELETE`. Never infer the target from a previously selected app. Accept custom positive RPS and minutes and a positive whole-number Muse-call cap. Copy the label **Muse calls** verbatim.

Use the bypass skill. Before calling any blackbox setup or start tool, get the exact target URL, allowed paths, allowed methods, request rate, Muse-call cap and time limit from this invocation through the sequential questions above. Ask only the next missing question and wait for its answer. Offer 120 Muse calls and 30 minutes as separate defaults; the user can say "default" for either. Always label the call cap "Muse calls", never another model's name. Do not use the native multiple-choice picker for numeric values: its custom answer can return a label instead of the number. A previously selected application is a suggestion only, never the target for a new audit. Do not silently use its saved URL. Show the selected values before starting. If no app is selected for the chosen target, call `bypass_connect_app` for an app-only profile; use `local` for a loopback URL and ask for the environment for a deployed URL. Use `bypass_blackbox_setup` for both new and existing scopes, including a setup-only request. Do not use `bypass_blackbox_scope`, `force`, or direct file edits to change rate, Muse calls or time: they can replace unrelated saved scope settings. Review the returned scope and complete any ownership or authorization steps it requires before testing.

When setup returns a production authorization step and the user explicitly approves that production scope, authorize with its `scope-file`, `accept:true`, and `production:true` together. Do not replace supplied values with defaults, and show the effective run limits. If the user asked only to prepare scope, do not start an audit. Give concise progress updates with actual counts. At completion inspect findings and coverage, then call `bypass_blackbox_verify` and `bypass_blackbox_export` for confirmed findings. Present each reported finding by its title and impact. Count corroborating route proofs as affected paths of the same issue, not separate vulnerabilities.
