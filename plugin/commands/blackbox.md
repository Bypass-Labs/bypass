Use the same choices-first setup as `/bypass:start`. Reuse a supplied URL. If only a saved app is known, offer **Use this app** / **Another app** with custom input; never silently switch or start an audit. An unknown URL is the one necessary text input. Connect an app-only profile with `bypass_connect_app` when needed and collect an unknown environment with its native picker.

Call `bypass_blackbox_setup` with `plan:true` and the known URL/environment and any explicit limits. This is read-only and returns the exact saved or proposed scope and the shared **Approve / Decline / Custom instructions** picker. Show the app, environment, paths, methods, rate, and run limits together. Approve means the user controls the app and authorizes that plan. Do not ask five separate configuration questions. Existing scope is reused; advanced settings appear only for Custom instructions. Preserve supplied values and custom notes. If the host returns a custom label without its value, ask for only that missing value, not the entire questionnaire. Numeric limits remain validated by the tools. A changed plan needs approval; a preselected option is not consent.

After approval, load the bypass skill for assessment and call `bypass_blackbox_setup` without plan using the returned arguments. Compare the prepared scope to the approved plan. Follow only its required verification/authorization steps; no DNS or HTTPS-file question when the project setting is off. Use each authorization step's exact scope-file, accept:true, and production:true only if the displayed production scope was approved. Decline saves no permission and runs nothing. Setup-only requests never start the audit. Do not replace scope with `force` or hand-edit state. If a custom request cannot be applied without replacing scope, explain that limitation before doing so.

Pass the target, allowed paths, selected methods and exact request rate to setup. Setup reuses an existing higher-rate scope when the user chooses a lower rate, and updates only the rate when the user chooses a higher one; preserve every other saved setting. When setup returns a production authorization step and the user explicitly approves that production scope, authorize with its `scope-file`, `accept:true`, and `production:true` together. Do not fall back to authorizing without the scope file: that would lose the selected methods and rate. Pass the chosen rate, Muse-call cap and time limit in minutes to `bypass_blackbox_start`. Pass other user-specified execution limits such as URL count, tasks and worker counts to start too. For a resume request, pass the user's new limits to `bypass_blackbox_resume`. Do not replace supplied values with defaults, and show the effective run limits. If the user asked only to prepare scope, do not start an audit. Continue with `bypass_blackbox_next`, carrying its progress cursor. Each pending request contains a bounded evidence prompt and JSON schema. Reason in this active Muse session and send one schema-shaped decision through `bypass_blackbox_submit` for each request ID. After context compaction, search tools for `bypass_blackbox_next` and `bypass_blackbox_submit`, use the identifiers returned by search, and continue the same run from its pending ID. Never construct a tool identifier or restart the audit to recover a missing tool. Continue until the audit is terminal. Never launch the standalone CLI, a nested Muse process, or an external model call. Bypass executes every scoped request and independently verifies findings.

Give concise progress updates with actual counts. At completion inspect findings and coverage, then call `bypass_blackbox_verify` and `bypass_blackbox_export` for confirmed findings. Present each reported finding by its title and impact. Count corroborating route proofs as affected paths of the same issue, not separate vulnerabilities. If saved research remains, use `bypass_blackbox_resume` when the user wants it continued. State untested work and failed proofs plainly. Keep credentials out of messages and artifacts.
